# Odoo Form Context Menu Customization Implementation Run Plan

## Document status

**Plan status:** `DRAFT`

**Execution status:** `NOT STARTED`

**Source requirement:** REQ-ODOO-FORM-CONTEXT-MENU-CUSTOMIZATION-DESIGN revision 1

**Product baseline:** `17a0c505e645d47babbf429528da3df2edbb5f1b`

Implement a standalone Odoo Community add-on that replaces the native context menu only on supported backend form surfaces, provides safe Odoo-aware navigation commands, exposes a stable registry-based extension contract, and ships the Go to the Main Table form item as an ordinary extension whose current behavior is limited to the approved modal placeholder. The work includes release-target confirmation, implementation, accessibility and localization, automated browser and unit coverage, clean-install and upgrade validation, and rollback documentation; actual Main Table navigation and non-form context menus remain out of scope.

## Architecture

### Platform and languages

Target the Owl-based Odoo Community Edition web client, with Odoo 19.0 as the approved reference design and a mandatory pre-implementation check against the deployed major version because `factory.yaml` does not yet pin one. Implement frontend behavior with Odoo JavaScript modules, Owl/XML templates, Odoo theme-compatible styles, translation resources, and the minimal Python manifest and initialization files required by an installable add-on. Use Odoo registries, services, HOOT, web test helpers, the mock server, and browser tests available in the confirmed product toolchain; add no Enterprise-only or third-party runtime dependency.

### Components and responsibilities

Create one independently installable add-on beneath `addons/`, using the repository's `customer_` module prefix after its exact technical name is confirmed in Phase 1. Keep all selected-release form-controller imports and calls in one form-context adapter. Keep the menu-item registry, single-menu coordinator, Owl menu component, styles, navigation provider, and Go to the Main Table form provider separate. The adapter registers and unregisters form roots, produces short-lived context snapshots, and exposes a narrow safe-navigation facade. The coordinator owns resolution, deterministic ordering, lifecycle, command dispatch, failure routing, and focus restoration. Providers contribute ordinary registry entries and may use only the documented service facade. Module-owned tests stay with the add-on; cross-module browser, installation, upgrade, and release tests stay under `tests/`.

### Data and integrations

The initial release adds no server model, persistent table, migration, controller, or database-configured executable source. Context snapshots are short-lived client objects; labels and disabled reasons render as text. Commands use Odoo action, dialog, notification, user, ORM/RPC, and adapter navigation services so server ACLs, record rules, CSRF/session handling, and unsaved-change guards remain authoritative. Menu opening and visibility or enabled predicates perform no RPC. The Go to the Main Table form callback opens the standard modal with body text exactly `Go to the Main Table form`, exposes one `Close` action, and performs no navigation.

### Repository and delivery constraints

- **Run-plan dependencies:**
  - None
- **Affected modules:**
  - New standalone form-context-menu add-on whose exact `customer_` technical name is confirmed in TASK-01-02
- **Allowed product paths:**
  - `factory.yaml`
  - `factory.lock`
  - `addons/**`
  - `tests/**`
  - `docs/**`
  - `deployment/**`
- **Forbidden paths:**
  - `.git/**`
  - `requirements/**`
  - `README.md`
  - `../**`
  - Odoo core source and unrelated existing add-on directories
- **Database concerns:**
  - No schema or persistent data is planned; clean-install and production-snapshot upgrade gates must prove that module installation, update, disablement, and removal need no data migration.
- **Known conflicts:**
  - The product contract leaves the Odoo version unresolved even though the approved design uses Odoo Community 19.0 as its reference baseline.
  - The organization browser support policy is not included in the supplied artifacts.
  - Third-party add-ons may patch the same form controller or intercept `contextmenu` events.
  - Replacing the browser menu inside form fields removes native spelling, editing, and inspection commands on those surfaces.
- **Deployment and rollback:** Install and update the add-on through the normal Odoo module and backend-asset process, first on a nonproduction database and then through the governed release path after all quality gates pass. Roll back by disabling or uninstalling the add-on and rebuilding backend assets; because the release adds no persistent model, no data rollback or migration is expected. Preserve exact product commits and store approvals, execution progress, and validation evidence only in the delivery repository.

## Implementation principles

- Intercept context-menu events only after a supported registered form root and a valid menu model are resolved; otherwise retain the native browser menu as the fail-safe.
- Isolate release-sensitive controller behavior in the adapter, reject executable database content and raw HTML, and keep authorization on normal Odoo service and server boundaries.
- Build every acceptance behavior into automated HOOT, component, integration, or browser coverage, including dirty records, dialogs, keyboard access, extension isolation, latency, clean installation, upgrade, and rollback readiness.

- [ ] **TASK-02-03 Implement the selected-release form context adapter**
  - **Status:** `NOT STARTED`

  - **Allowed paths:**

  - **Verification:**

  - **Deliverable:** Navigation provider and facade implementations with clean, dirty, new, first, middle, and last record coverage.
  - **Allowed paths:**
    - `addons/**`
  - **Verification:**
    - Test command ordering, availability, disabled states, and Back, Previous, Next, and Refresh outcomes against the mounted form controller.
    - Verify no implementation uses browser history, full-window reload, route mutation without controller state, or simulated toolbar or pager clicks.
    - Verify dirty and new records cannot silently lose edits.
